# SQL 语法自动修复设计文档

## 上下文

### 背景
在 Oracle SQL 转 MySQL 的过程中，虽然已经有转换工具（`convert_oracle_sql.py`），但转换后的 SQL 文件在实际导入时仍会遇到语法错误，主要原因：

1. **MySQL 保留字冲突**：Oracle 中合法的列名（如 `describe`、`condition`、`key` 等）在 MySQL 中是保留字
2. **数据类型细微差异**：某些数据类型的长度限制和默认值不同
3. **转换工具局限**：基于正则表达式的转换无法处理所有边界情况

### 约束
- 必须保持向后兼容，不能影响现有的导入流程
- 修复规则必须安全，不能改变 SQL 语句的语义
- 性能开销要小，不能显著增加导入时间

### 利益相关者
- 数据库管理员：需要快速、可靠地导入大量 SQL 文件
- 开发人员：需要调试和了解修复的具体内容

## 目标 / 非目标

### 目标
- ✅ 自动修复 MySQL 保留字冲突问题
- ✅ 自动修复常见的语法错误（日期格式、字符串转义等）
- ✅ 提供修复报告，便于审计和调试
- ✅ 支持将修复后的 SQL 保存到文件

### 非目标
- ❌ 修复逻辑错误（如业务规则不正确）
- ❌ 优化 SQL 性能
- ❌ 重构 SQL 结构
- ❌ 处理 PL/SQL 或存储过程（这些应该在转换阶段处理）

## 决策

### 决策 1：修复器架构

**选择**：创建独立的 `SQLSyntaxFixer` 类，与导入流程解耦

**理由**：
- 单一职责原则：修复逻辑与导入逻辑分离
- 便于测试：可以独立测试修复规则
- 便于扩展：可以轻松添加新的修复规则
- 可复用：其他命令也可以使用这个修复器

### 决策 2：MySQL 保留字处理策略

**选择**：使用正则表达式 + 上下文检测

**理由**：
- 正则表达式效率高
- 上下文检测避免误判（如字符串内的保留字不应修复）

**实现策略**：
```python
# 1. 定义 MySQL 保留字列表（8.0 版本）
MYSQL_RESERVED_WORDS = {
    'describe', 'key', 'condition', 'index', 'table', 
    'database', 'select', 'insert', 'update', 'delete',
    'where', 'order', 'group', 'having', 'join', 
    'from', 'to', 'as', 'and', 'or', 'not', 
    'in', 'exists', 'between', 'like', 'is', 
    'null', 'default', 'check', 'primary', 'foreign',
    'unique', 'constraint', 'references', 'cascade',
    'precision', 'read', 'write', 'schema', 'trigger',
    'procedure', 'function', 'view', 'grant', 'revoke',
    # ... 更多保留字
}

# 2. 检测位置：
# - CREATE TABLE 语句中的列名
# - CREATE TABLE 语句中的表名
# - INSERT INTO 语句中的列名

# 3. 不修复的位置：
# - 字符串字面量内（单引号内）
# - 注释内
# - 已经用反引号包裹的
```

### 决策 3：修复时机

**选择**：在执行前修复（内存中）

**替代方案**：
1. **修改源文件**：直接修改 SQL 文件
   - ❌ 破坏性操作，不可逆
   - ❌ 可能需要版本控制
   
2. **先生成修复文件，再导入**：两阶段处理
   - ✅ 安全，可以审查修复结果
   - ❌ 增加磁盘 I/O
   - ✅ 通过 `--save-fixed` 参数支持这种模式

3. **执行前内存修复**（选择）
   - ✅ 快速，不产生额外文件
   - ✅ 不修改源文件
   - ✅ 可选保存到新文件

### 决策 4：修复规则优先级

**规则列表**（按执行顺序）：

1. **MySQL 保留字修复**（优先级：高）
   - 示例：`describe VARCHAR(100)` → `` `describe` VARCHAR(100) ``
   - 检测范围：CREATE TABLE、INSERT INTO

2. **数据类型修复**（优先级：中）
   - `VARCHAR2` → `VARCHAR`（已在转换阶段处理，这里作为兜底）
   - `NUMBER(p,s)` → `DECIMAL(p,s)`

3. **日期格式修复**（优先级：低）
   - `TO_DATE` → `STR_TO_DATE`（已在转换阶段处理，这里作为兜底）

4. **字符串转义修复**（优先级：低）
   - 处理单引号转义问题

## 风险 / 权衡

| 风险 | 影响 | 缓解措施 |
|------|------|---------|
| 过度修复（误判） | 可能改变 SQL 语义 | 严格限制修复范围，只处理明确的保留字冲突 |
| 修复不完全 | 导入仍然失败 | 提供详细的错误提示，建议手动修复 |
| 性能开销 | 导入变慢 | 使用高效的正则表达式，避免复杂的解析 |
| 修复规则维护 | 需要持续更新 | 使用配置文件管理保留字列表 |

## 迁移计划

### 步骤
1. **实现修复器**：独立模块，不影响现有功能
2. **添加可选参数**：`--auto-fix`，默认禁用
3. **内部测试**：使用实际的错误 SQL 文件测试
4. **逐步启用**：先在开发环境测试，确认无误后推广

### 回滚
- 如果自动修复导致问题，移除 `--auto-fix` 参数即可回退到原有行为
- 不影响已导入的数据（修复只在内存中进行）

## 待决问题

   - 当前方案：硬编码在代码中

   - 决策：初版硬编码，后续根据需要扩展

2. **是否需要修复结果的交互式确认？**
   - 当前方案：自动修复，可选生成报告
   - 备选方案：每次修复前询问用户
   - 决策：自动修复 + 报告，避免打断导入流程

3. **是否需要支持自定义修复规则？**
   - 当前方案：内置规则
   - 备选方案：允许用户编写 Python 插件
   - 决策：初版不支持，后续根据需求评估
