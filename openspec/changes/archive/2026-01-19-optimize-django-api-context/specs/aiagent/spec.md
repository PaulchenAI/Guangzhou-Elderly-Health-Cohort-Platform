# aiagent 规范增量

## 新增需求

### 需求：分层 API 上下文管理

系统必须支持分层的 API 上下文管理，避免一次性加载所有 API 端点导致上下文超限。

#### 场景：生成紧凑 API 摘要

- **当** API 端点数量超过配置阈值（默认 50 个）
- **那么** 系统必须生成紧凑摘要，仅包含 Tag 统计和描述
- **并且** 紧凑摘要的 Token 数量必须控制在配置限制内

#### 场景：按 Tag 加载端点摘要

- **当** LLM 选择了特定的 API Tag
- **那么** 系统必须加载该 Tag 下所有端点的摘要
- **并且** 摘要包含端点路径、方法、简要描述
- **并且** 不包含完整的参数和响应定义

#### 场景：按需加载端点详情

- **当** LLM 确定要调用的具体 API 端点
- **那么** 系统必须加载该端点的完整详情
- **并且** 详情包含所有参数定义和响应结构

#### 场景：上下文 Token 限制

- **当** 生成 API 摘要时
- **那么** 系统必须估算 Token 数量
- **并且** 超过配置限制时自动切换到紧凑模式
- **并且** 支持通过 `DJANGO_API_CONTEXT_TOKEN_LIMIT` 配置限制值

---

### 需求：执行记录持久化存储

系统必须支持将所有执行记录（成功和失败）持久化保存，便于后续 RAG 检索和错误学习。

#### 场景：保存成功执行记录

- **当** 脚本生成器成功执行脚本
- **那么** 系统必须自动保存执行记录到配置的目录
- **并且** 记录包含：意图、脚本内容、执行结果、使用的 API
- **并且** 状态标记为 `success`

#### 场景：保存失败执行记录

- **当** 脚本生成器执行失败
- **那么** 系统必须自动保存执行记录到配置的目录
- **并且** 记录包含：意图、脚本内容、错误信息、错误类型
- **并且** 状态标记为 `failed` 或 `error`
- **并且** 错误类型分类包括：参数错误、API不存在、权限不足、网络错误等

#### 场景：保存执行记录元数据

- **当** 保存执行记录时
- **那么** 系统必须保存完整元数据
- **并且** 元数据包含：意图、API 列表、状态、结果/错误、时间戳
- **并且** 元数据格式为 JSON

#### 场景：配置存储目录

- **当** 需要自定义存储位置
- **那么** 用户可以通过 `DJANGO_API_HISTORY_DIR` 环境变量配置
- **并且** 默认目录为 `data/execution_history/`

#### 场景：禁用记录保存

- **当** 用户不希望保存执行记录
- **那么** 可以通过 CLI 参数 `--no-save` 禁用保存
- **并且** 可以通过环境变量 `DJANGO_API_HISTORY_SAVE=false` 全局禁用

---

### 需求：历史指令 RAG 检索复用

系统必须将历史执行记录（成功和失败）作为 RAG 知识源，每次新指令必须强制优先检索历史相似指令。

#### 场景：构建历史指令向量索引

- **当** 保存新执行记录后
- **那么** 系统必须为执行记录生成向量表示
- **并且** 向量内容包括意图描述、API 列表、执行状态
- **并且** 成功和失败记录都必须索引
- **并且** 支持增量更新索引

#### 场景：强制优先检索历史指令

- **当** 用户提交新的查询意图
- **那么** 系统必须在生成脚本前**强制**先检索历史指令
- **并且** 返回相似的成功记录和失败记录
- **并且** 包含相似度分数和执行状态

---

### 需求：相似度计算

系统必须提供多维度加权的相似度计算能力，准确匹配历史指令。

#### 场景：意图归一化处理

- **当** 计算意图相似度前
- **那么** 系统必须对意图进行归一化处理
- **并且** 提取核心意图（去除数目、翻页等参数信息）
- **并且** "查询用户列表前10个"归一化为"查询用户列表"
- **并且** "查询第2页用户"归一化为"查询用户列表"
- **并且** 保留原始参数信息用于脚本复用时的参数替换

#### 场景：参数信息提取

- **当** 对意图进行归一化处理时
- **那么** 系统必须提取以下参数信息：
  - 数目参数：前N个、N条、limit N
  - 翻页参数：第N页、page N
  - 排序参数：按X排序、倒序
- **并且** 将提取的参数信息与核心意图分开存储

#### 场景：向量余弦相似度计算

- **当** 需要计算两个意图的相似度
- **那么** 系统必须使用归一化后的核心意图进行向量计算
- **并且** 使用 Embedding 模型将意图文本转换为向量
- **并且** 使用余弦相似度公式计算向量相似度
- **并且** 相似度结果归一化到 [0, 1] 范围

#### 场景：多维度加权相似度

- **当** 需要更精确的相似度计算
- **那么** 系统必须综合多个维度计算加权相似度
- **并且** 语义相似度权重默认 0.7
- **并且** API 重合度权重默认 0.2（使用 Jaccard 系数）
- **并且** 关键词匹配权重默认 0.1
- **并且** 权重可通过配置文件调整

#### 场景：相似度权重配置

- **当** 需要调整相似度计算策略
- **那么** 用户可以通过配置文件设置各维度权重
- **并且** 支持 `HISTORY_WEIGHT_SEMANTIC`、`HISTORY_WEIGHT_API`、`HISTORY_WEIGHT_KEYWORD` 配置项

---

### 需求：检索结果分层处理

系统必须根据相似度分数将检索结果分层，采用不同的处理策略。

#### 场景：精确匹配层处理

- **当** 检索到相似度 ≥ 0.95 的成功历史记录
- **那么** 系统必须将其标记为精确匹配
- **并且** 提示可直接复用该脚本
- **并且** 跳过脚本生成流程
- **并且** 自动替换参数（将历史脚本中的数目、翻页参数替换为当前意图的参数）
- **并且** 阈值可通过 `HISTORY_EXACT_THRESHOLD` 配置

#### 场景：参数自动替换

- **当** 复用历史脚本时
- **那么** 系统必须将历史脚本中的参数替换为当前意图的参数
- **并且** 替换数目参数（如 limit 从 5 改为 10）
- **并且** 替换翻页参数（如 page 从 1 改为 2）
- **并且** 替换排序参数（如有）
- **例如** 历史脚本 `limit=5`，当前意图"前10个"，替换为 `limit=10`

#### 场景：高度相似层处理

- **当** 检索到相似度在 0.80 - 0.95 之间的历史记录
- **那么** 系统必须将其标记为高度相似
- **并且** 成功记录作为主要参考模板提供给 LLM
- **并且** 失败记录提取错误原因告知 LLM 避免
- **并且** 阈值可通过 `HISTORY_HIGH_THRESHOLD` 配置

#### 场景：一般相似层处理

- **当** 检索到相似度在 0.60 - 0.80 之间的历史记录
- **那么** 系统必须将其标记为一般相似
- **并且** 仅作为辅助参考，不直接使用代码
- **并且** 阈值可通过 `HISTORY_LOW_THRESHOLD` 配置

#### 场景：不相关记录过滤

- **当** 检索到相似度 < 0.60 的历史记录
- **那么** 系统必须过滤掉这些记录
- **并且** 不将其加入 LLM 上下文

#### 场景：分层上下文构建

- **当** 完成检索结果分层后
- **那么** 系统必须根据分层结果构建 LLM 上下文
- **并且** 精确匹配层最多返回 1 条记录
- **并且** 高度相似层最多返回 3 条记录
- **并且** 一般相似层最多返回 2 条记录
- **并且** 返回数量可通过配置调整

---

### 需求：历史记录管理

系统必须提供历史记录的生命周期管理能力。

#### 场景：历史记录自动清理

- **当** 执行记录超过保留期限
- **那么** 系统必须自动清理过期记录
- **并且** 保留期限可通过 `DJANGO_API_HISTORY_RETENTION_DAYS` 配置
- **并且** 默认保留 30 天

#### 场景：学习失败历史记录

- **当** 检索到相似的失败执行记录
- **那么** 系统必须将失败记录的错误信息作为上下文提供给 LLM
- **并且** 告知 LLM 避免重复同样的错误
- **并且** 包含错误类型和错误原因

---

### 需求：查询结果默认翻页

系统必须在查询没有明确数目时自动添加翻页参数，避免返回大量数据导致性能问题。

#### 场景：检测用户意图中的数目

- **当** 用户提交查询意图
- **那么** 系统必须分析意图是否包含明确数目
- **并且** 识别"前N个"、"全部"、"第N页"等数目表达
- **并且** 无明确数目时标记为需要默认翻页

#### 场景：自动添加默认翻页参数

- **当** 用户意图没有明确数目
- **并且** API 端点支持分页参数
- **那么** 系统必须自动添加翻页参数
- **并且** 默认 `page=1`，`pageSize=10`
- **并且** 在生成的脚本中包含翻页参数

#### 场景：配置默认翻页值

- **当** 需要调整默认翻页参数
- **那么** 用户可以通过 `DJANGO_API_DEFAULT_PAGE_SIZE` 配置每页数量
- **并且** 可以通过 `DJANGO_API_DEFAULT_PAGE` 配置默认页码
- **并且** 默认值为 `page=1`，`pageSize=10`

#### 场景：保留用户指定的数目

- **当** 用户意图包含明确数目（如"查询前20个"）
- **那么** 系统必须使用用户指定的数目
- **并且** 不覆盖用户的翻页参数

#### 场景：返回结果包含翻页信息

- **当** 查询返回分页数据
- **那么** 系统必须在结果中包含翻页参数说明
- **并且** 包含当前页码 `page`
- **并且** 包含每页数量 `pageSize`
- **并且** 包含总记录数 `total`
- **并且** 包含总页数 `totalPages`
- **并且** 包含是否有下一页 `hasMore`

#### 场景：提示用户翻页操作

- **当** 返回结果不是最后一页
- **那么** 系统必须在输出中提示用户可以继续查询下一页
- **并且** 显示剩余未返回的记录数
- **例如** "当前返回第 1 页，共 10 条。总计 156 条记录，还有 146 条未显示。可输入'下一页'或'查询第2页'继续查看。"

---

### 需求：输出格式支持

系统必须支持多种输出格式，满足不同使用场景的需求。

#### 场景：默认文本格式输出

- **当** 用户未指定输出格式
- **那么** 系统必须使用友好的文本格式输出
- **并且** 包含格式化的数据展示和翻页提示

#### 场景：JSON 格式输出

- **当** 用户指定 `--json` 或 `--output json` 参数
- **那么** 系统必须输出结构化的 JSON 格式
- **并且** 包含 `data`（查询数据）、`pagination`（翻页信息）、`meta`（元信息）
- **并且** JSON 格式便于程序化处理和管道操作

#### 场景：JSON 输出结构

- **当** 输出 JSON 格式
- **那么** 必须包含以下字段：
  - `success`: 是否成功（boolean）
  - `data`: 查询结果数据（array）
  - `pagination`: 翻页信息对象
  - `meta`: 元信息（意图、API、耗时等）
- **并且** 翻页信息包含 page、pageSize、total、totalPages、hasMore

#### 场景：配置默认输出格式

- **当** 需要修改默认输出格式
- **那么** 用户可以通过 `DJANGO_API_OUTPUT_FORMAT` 环境变量配置
- **并且** 支持的值为 `text`（默认）或 `json`
