# SQL 转换工具优化规范

## 新增需求

### 需求：跳过已转换文件

系统必须在转换前检查输出文件是否已存在，如果存在则跳过转换。

#### 场景：文件已存在

- **当** 用户使用 `--skip-existing` 参数且输出文件已存在
- **那么** 执行严格的完整性检查，只有通过所有检查才跳过转换

#### 场景：严格的完整性检查

- **当** 检查文件完整性时
- **那么** 必须通过以下所有检查：
  1. 文件大小 >= 100 字节（避免空文件或截断文件）
  2. 文件开头必须包含 `CREATE TABLE` 语句
  3. 文件末尾必须以分号（`;`）结尾
  4. 文件末尾不能有未完成的语句（如未闭合的引号）
  5. 文件必须包含至少一个 `CREATE TABLE` 语句
  6. **INSERT 语句数量核对**：目标文件中的 INSERT 数量必须与源文件匹配（允许 1% 误差）

#### 场景：文件不完整

- **当** 文件已存在但任何一项检查失败
- **那么** 记录警告信息，说明失败原因，并重新转换该文件

#### 场景：检查失败原因

- **当** 完整性检查失败
- **那么** 在日志中显示具体的失败原因：
  - "文件不完整：缺少 CREATE TABLE"
  - "文件不完整：未以分号结尾"
  - "文件不完整：可能有未完成的语句"
  - "文件不完整：文件太小（X 字节）"
  - "文件不完整：INSERT 数量不匹配（源文件: X，目标文件: Y）"
  - "文件不完整：缺少 INSERT 语句（源文件有 X 个）"
  - "文件检查失败: [错误信息]"

#### 场景：强制重新转换

- **当** 用户使用 `--force` 参数
- **那么** 即使文件已存在，也重新转换

#### 场景：显示跳过信息

- **当** 跳过已存在的文件
- **那么** 在日志中显示 `[跳过] 文件名（已存在）`

---

### 需求：内存优化

系统必须优化大文件处理时的内存使用，避免内存溢出导致进程被 killed。

#### 场景：流式处理

- **当** 处理大文件（>10MB）
- **那么** 使用逐行读取或分批处理，避免一次性加载整个文件

#### 场景：及时释放内存

- **当** 处理完一个文件
- **那么** 及时释放文件内容和转换结果，避免内存累积

---

### 需求：错误恢复

系统必须在单个文件失败时继续处理，并在最后提供完整的失败报告。

#### 场景：单个文件失败

- **当** 某个文件转换失败（内存不足、语法错误等）
- **那么** 记录错误信息，继续处理下一个文件

#### 场景：最终报告

- **当** 批量转换完成
- **那么** 输出完整报告：成功数、失败数、跳过数、失败文件列表

---

### 需求：详细的转换结果输出

系统必须在转换成功时输出详细的转换结果信息。

#### 场景：显示转换统计

- **当** 文件转换成功
- **那么** 在日志中显示转换的语句数量和输出文件大小

#### 场景：输出格式

- **当** 转换成功
- **那么** 显示格式：`[成功] 已写入 X 个语句到文件`，并显示输出文件大小（MB）

---

### 需求：进度显示

系统必须在批量转换过程中显示详细的进度信息。

#### 场景：显示进度条和百分比

- **当** 批量转换进行中
- **那么** 显示进度条、当前进度（已处理/总数）和百分比

#### 场景：进度条格式

- **当** 处理文件时
- **那么** 显示格式：`[i/total] [████████░░░░░░░░] XX.X% - 处理: 文件名`

#### 场景：单文件转换进度

- **当** 转换大文件（>10MB）时
- **那么** 显示单文件转换进度：
  - 开始时显示：`开始转换大文件（X.X MB），请稍候...`
  - 每 10000 个语句显示：`进度: 已转换 X,XXX 个语句，文件读取 XX.X%`
  - 完成时显示：`转换完成: 共处理 X,XXX 行，转换 X,XXX 个语句`

## 新增需求

### 需求：完整性检查的 INSERT 数量统计

系统必须准确统计目标文件中的 INSERT 语句数量，包括大文件（>10MB）。

#### 场景：大文件使用流式统计

- **当** 检查大文件（>10MB）的完整性时
- **那么** 必须使用流式逐行统计 INSERT 数量，而非只读取部分内容
- **并且** 统计准确率必须达到 100%

#### 场景：小文件读取全部内容

- **当** 检查小文件（<10MB）的完整性时
- **那么** 可以读取全部内容并使用 `count()` 方法统计

#### 场景：避免内存溢出

- **当** 统计 INSERT 数量时
- **那么** 对于大文件必须使用 O(1) 空间复杂度的流式处理
- **并且** 不能一次性加载整个文件到内存

---

### 需求：|| 连接符转换性能优化

系统必须优化 `||` 连接符转换逻辑，避免正则表达式导致的灾难性回溯。

#### 场景：跳过复杂语句

- **当** INSERT 语句包含超过 20 个单引号时
- **那么** 跳过 `||` 连接符转换，避免性能问题

#### 场景：限制字符串长度

- **当** 转换 `||` 连接符时
- **那么** 只匹配长度 ≤ 100 字符的字符串
- **并且** 避免使用嵌套量词的复杂正则表达式

#### 场景：限制替换次数

- **当** 处理包含多个 `||` 的语句时
- **那么** 最多替换 3 次
- **并且** 每次只替换 1 个匹配，及时检测无变化并退出

#### 场景：性能保证

- **当** 转换任意大小的文件时
- **那么** 单个 INSERT 语句的转换时间必须 < 10 毫秒
- **并且** 不能出现 CPU 100% 但无进展的情况
