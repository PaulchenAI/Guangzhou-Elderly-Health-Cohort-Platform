# sql-import 规范增量

## 新增需求

### 需求：多策略外键信息提取

系统必须提供从 SQL 文件中提取外键约束信息的能力，支持多种提取策略以适应不同格式，并优化大文件处理。

#### 场景：大文件识别

- **当** 读取 SQL 文件
- **那么** 检查文件大小（以 MB 为单位）
- **并且** 标记大于 1MB 的文件为"大文件"

#### 场景：大文件关键字片段提取

- **当** 处理大文件（>1MB）
- **那么** 使用流式处理逐行读取文件
- **并且** 搜索外键相关关键字：`foreign key`、`references`、`add constraint`、`constraint.*foreign`
- **并且** 提取包含关键字的行及其上下文（前后各 5-10 行）
- **并且** 确保语句完整性（查找分号边界）
- **并且** 最多提取 5 个示例片段
- **并且** 去除重复片段

#### 场景：小文件完整读取

- **当** 处理小文件（≤1MB）
- **那么** 直接读取完整文件内容
- **并且** 使用正则表达式提取所有外键语句

#### 场景：大文件流式应用提取脚本

- **当** 需要对大文件应用提取脚本
- **那么** 使用流式处理逐块读取文件
- **并且** 在内存中只保留当前处理块
- **并且** 累积提取结果而非累积文件内容
- **并且** 确保内存占用 < 100MB

#### 场景：策略 1 - 标准正则表达式提取

- **当** 读取包含标准格式 `alter table ... add constraint ... foreign key` 语句的 SQL 文件
- **那么** 使用正则表达式解析并提取外键的完整元数据信息（约束名、源表、源字段、目标表、目标字段、删除规则）
- **并且** 评估提取结果的置信度

#### 场景：策略 2 - 格式变体脚本提取

- **当** 标准正则表达式提取失败或置信度低于 0.9
- **那么** 计算文件的格式指纹
- **并且** 在已知格式变体脚本库中查找匹配的提取脚本
- **并且** 使用匹配的脚本进行提取

#### 场景：策略 3 - LLM 辅助脚本生成

- **当** 标准策略和格式变体脚本都无法成功提取
- **那么** 提取包含外键定义的语句块（2-3 个示例）
- **并且** 调用 Claude API 分析格式并生成 Python 提取脚本
- **并且** 验证生成的脚本（语法检查 + 功能测试）
- **并且** 将验证通过的脚本缓存到策略库

#### 场景：策略优先级和回退

- **当** 某个策略提取失败
- **那么** 按优先级依次尝试下一个策略（标准正则 → 格式变体 → LLM 生成）
- **并且** 记录每个文件使用的策略
- **并且** 在最终报告中显示策略使用统计

#### 场景：格式指纹计算

- **当** 需要识别 SQL 文件格式
- **那么** 分析以下特征：
  - 是否包含 `alter table` 关键字
  - 是否包含 `constraint` 关键字
  - 外键语句数量
  - 语句是否包含换行符
  - 关键字出现顺序
- **并且** 生成 8 位哈希指纹

#### 场景：支持单字段外键

- **当** 解析到单字段外键（如 `foreign key (PARENTID) references BS_DEPARTMENT (MAINID)`）
- **那么** 提取源字段为 `["PARENTID"]`，目标字段为 `["MAINID"]`

#### 场景：支持复合字段外键

- **当** 解析到复合字段外键（如 `foreign key (LISTNO, DETAILNO) references TABLE (ID1, ID2)`）
- **那么** 提取源字段为 `["LISTNO", "DETAILNO"]`，目标字段为 `["ID1", "ID2"]`

#### 场景：提取删除规则

- **当** 解析到 `on delete cascade` 子句
- **那么** 记录删除规则为 `"cascade"`
- **当** 解析到 `on delete set null` 子句
- **那么** 记录删除规则为 `"set_null"`
- **当** 没有 `on delete` 子句
- **那么** 删除规则为 `null`

#### 场景：支持自引用外键

- **当** 外键引用的目标表是表本身（如 `BS_CHECK_TYPE` 引用 `BS_CHECK_TYPE`）
- **那么** 正确识别为自引用外键，源表和目标表名称相同

#### 场景：忽略大小写

- **当** SQL 语句使用任意大小写（如 `ALTER TABLE`、`alter table`、`Alter Table`）
- **那么** 正确解析外键信息，统一转为大写存储

### 需求：LLM 辅助脚本生成

系统必须集成 LLM（Claude API）分析未知格式并生成提取脚本，并优化大文件场景的 Token 使用。

#### 场景：大文件片段发送给 LLM

- **当** 需要为大文件生成提取脚本
- **那么** 只发送关键字提取的片段给 LLM（而非整个文件）
- **并且** 限制发送的总 Token 数 < 4000
- **并且** 在提示词中说明这些是从大文件中提取的片段

#### 场景：调用 Claude API 生成脚本

- **当** 需要为未知格式生成提取脚本
- **那么** 构建包含以下内容的提示词：
  - 2-3 个外键语句片段（如果是大文件，标注已提取片段）
  - 要提取的字段说明
  - Python 函数模板要求（支持流式处理大文件）
  - 输出格式规范
- **并且** 调用 Claude API（claude-3-5-sonnet-20241022）
- **并且** 设置温度参数为 0.1 以确保一致性
- **并且** 提取返回内容中的代码块

#### 场景：验证生成的脚本

- **当** LLM 生成提取脚本
- **那么** 执行以下验证步骤：
  1. 语法检查：使用 `compile()` 验证 Python 语法
  2. 函数存在性检查：确认包含 `extract_foreignkeys` 函数
  3. 功能测试：使用示例语句测试提取功能
  4. 返回格式检查：验证返回列表且包含必需字段
  5. 字段完整性检查：确认每个外键包含必需字段
- **并且** 只有所有验证通过才使用该脚本

#### 场景：LLM 重试机制

- **当** LLM 生成的脚本验证失败
- **那么** 最多重试 2 次（共 3 次尝试）
- **并且** 记录每次失败的原因
- **并且** 如果所有重试都失败，标记该文件为"无法提取"

#### 场景：API 密钥配置

- **当** 用户启用 LLM 功能（`--enable-llm`）
- **那么** 从以下来源获取 API 密钥（按优先级）：
  1. 命令行参数 `--anthropic-api-key`
  2. 环境变量 `ANTHROPIC_API_KEY`
- **当** 未配置 API 密钥且需要 LLM
- **那么** 跳过 LLM 策略，输出警告信息

#### 场景：API 调用失败处理

- **当** Claude API 调用失败（网络错误、配额超限、认证失败）
- **那么** 记录详细错误信息
- **并且** 将该文件标记为"LLM 提取失败"
- **并且** 在最终报告中列出所有 LLM 失败的文件

---

### 需求：提取策略缓存管理

系统必须缓存 LLM 生成的提取脚本，避免重复分析相同格式。

#### 场景：策略缓存目录结构

- **当** 首次运行外键提取
- **那么** 创建策略缓存目录 `docs/hospital/foreignkey/generated_strategies/`
- **并且** 包含以下文件：
  - `{fingerprint}.py`：LLM 生成的提取脚本
  - `metadata.json`：格式指纹和脚本映射关系
  - `test_cases.json`：每个格式的测试用例

#### 场景：缓存命中

- **当** 计算出文件的格式指纹
- **并且** 该指纹存在于 `metadata.json` 中
- **那么** 加载对应的缓存脚本
- **并且** 直接使用该脚本提取外键
- **并且** 更新该策略的成功使用计数

#### 场景：缓存保存

- **当** LLM 生成的脚本验证通过
- **那么** 将脚本保存到 `{fingerprint}.py` 文件
- **并且** 更新 `metadata.json`，包含：
  - 格式指纹
  - 脚本文件路径
  - 格式描述
  - 创建时间
  - 成功使用计数
  - 样本文件名
- **并且** 保存测试用例到 `test_cases.json`

#### 场景：策略元数据更新

- **当** 使用缓存脚本成功提取
- **那么** 增加该策略的 `success_count` 计数
- **并且** 更新 `last_used_at` 时间戳

#### 场景：强制重新生成

- **当** 用户使用 `--force-regenerate` 参数
- **那么** 忽略缓存的脚本
- **并且** 重新调用 LLM 生成新脚本
- **并且** 覆盖旧的缓存文件

### 需求：外键信息 JSON 保存

系统必须将提取的外键信息保存为结构化 JSON 文件。

#### 场景：按表存储模式（默认）

- **当** 使用 `--mode per-table` 参数或不指定模式
- **那么** 为每个包含外键的表生成单独的 JSON 文件
- **并且** 文件名格式为 `{表名}_foreignkeys.json`（如 `BS_DEPARTMENT_foreignkeys.json`）

#### 场景：统一存储模式

- **当** 使用 `--mode unified` 参数
- **那么** 所有外键信息保存到一个 JSON 文件
- **并且** 默认文件名为 `all_foreignkeys.json`
- **并且** 包含元数据（提取时间、总文件数、总外键数、有外键的表数量）

#### 场景：JSON 结构（按表存储）

- **当** 保存单表外键信息
- **那么** JSON 结构必须包含：
  - `table_name`：表名
  - `source_file`：源 SQL 文件名
  - `extraction_strategy`：使用的提取策略（`standard_regex`、`variant_script`、`llm_generated`）
  - `strategy_fingerprint`：格式指纹（LLM 生成策略时）
  - `foreign_keys`：外键数组
    - `constraint_name`：约束名称
    - `source_table`：源表名
    - `source_columns`：源字段数组
    - `target_table`：目标表名
    - `target_columns`：目标字段数组
    - `on_delete`：删除规则（可选）
  - `extracted_at`：提取时间（ISO 8601 格式）

#### 场景：JSON 格式化

- **当** 保存 JSON 文件
- **那么** 使用 4 空格缩进，确保可读性
- **并且** 按字段名排序（`ensure_ascii=False` 支持中文）

#### 场景：无外键表处理

- **当** SQL 文件不包含外键约束
- **那么** 不生成 JSON 文件（按表存储模式）
- **或** 不添加到 `foreignkeys` 数组（统一存储模式）

### 需求：单文件外键提取命令

系统必须提供命令行工具，支持提取单个 SQL 文件的外键信息。

#### 场景：提取单个文件

- **当** 用户执行 `python -m AIagent.sql_import extract-foreignkey <sql_file> -o <output_dir>`
- **那么** 解析该 SQL 文件的外键信息
- **并且** 保存到指定输出目录

#### 场景：指定输出目录

- **当** 使用 `-o` 或 `--output` 参数指定输出目录（如 `docs/hospital/foreignkey/`）
- **那么** JSON 文件保存到该目录
- **并且** 如果目录不存在，自动创建

#### 场景：文件已存在处理

- **当** 输出文件已存在且未使用 `--overwrite` 参数
- **那么** 提示用户文件已存在，跳过保存
- **当** 使用 `--overwrite` 参数
- **那么** 覆盖已存在的文件

#### 场景：提取成功输出

- **当** 提取成功
- **那么** 输出：
  - 表名
  - 外键数量
  - 保存的文件路径

#### 场景：提取失败处理

- **当** SQL 文件不存在
- **那么** 输出错误信息并退出
- **当** SQL 文件无外键
- **那么** 输出提示"未找到外键信息"

### 需求：批量外键提取命令

系统必须支持批量提取目录下所有 SQL 文件的外键信息。

#### 场景：批量提取

- **当** 用户执行 `python -m AIagent.sql_import extract-foreignkey-all <sql_dir> -o <output_dir>`
- **那么** 遍历该目录下所有 `.sql` 文件
- **并且** 为每个文件自动选择合适的提取策略
- **并且** 提取每个文件的外键信息并保存

#### 场景：指定存储模式

- **当** 使用 `--mode per-table` 参数
- **那么** 为每个表生成单独的 JSON 文件
- **当** 使用 `--mode unified` 参数
- **那么** 所有外键信息保存到一个文件

#### 场景：启用 LLM 辅助

- **当** 使用 `--enable-llm` 参数
- **那么** 对于标准策略失败的文件，启用 LLM 辅助生成提取脚本
- **当** 不使用 `--enable-llm` 参数
- **那么** 只使用标准正则和格式变体脚本，跳过 LLM 策略

#### 场景：自定义统一文件名

- **当** 使用 `--mode unified --output-file custom_name.json` 参数
- **那么** 统一文件名为 `custom_name.json`

#### 场景：显示进度和策略信息

- **当** 批量提取进行中且使用 `--verbose` 参数
- **那么** 显示当前进度（已处理/总文件数）、当前文件名、外键数量、使用的策略

#### 场景：生成统计报告

- **当** 批量提取完成
- **那么** 输出汇总报告：
  - 总文件数和大文件数量（>1MB）
  - 有外键的表数量
  - 无外键的表数量
  - 总外键数量
  - 策略使用统计（标准正则、格式变体、LLM 生成各自的使用次数）
  - LLM API 调用次数和成本估算（如果启用）
  - 大文件处理统计（平均片段提取时间）
  - 生成的 JSON 文件数量（按表存储模式）
  - 输出目录路径

#### 场景：策略使用统计

- **当** 使用 `--show-strategies` 参数
- **那么** 在报告中显示每个文件使用的策略
- **并且** 输出策略分布统计（饼图或表格）

#### 场景：错误处理

- **当** 某个文件所有策略都提取失败
- **那么** 记录错误日志（文件名、尝试的策略、失败原因）
- **并且** 继续处理下一个文件
- **并且** 在最终报告中列出失败的文件

#### 场景：LLM 提取失败的文件列表

- **当** 批量提取完成且有 LLM 提取失败的文件
- **那么** 在报告中单独列出这些文件
- **并且** 提示用户检查这些文件或手动处理

### 需求：策略使用查询命令

系统必须提供命令查看策略使用情况和缓存统计。

#### 场景：查看策略统计

- **当** 用户执行 `python -m AIagent.sql_import foreignkey-stats`
- **那么** 显示以下统计信息：
  - 缓存的策略数量
  - 每个策略的成功使用次数
  - 每个策略的创建时间和最后使用时间
  - 每个策略对应的样本文件

#### 场景：查看策略详情

- **当** 用户执行 `python -m AIagent.sql_import foreignkey-stats --strategy <fingerprint>`
- **那么** 显示该策略的详细信息：
  - 格式指纹
  - 格式描述
  - 生成脚本的路径
  - 测试用例
  - 使用该策略的所有文件列表

#### 场景：清理无效策略

- **当** 用户执行 `python -m AIagent.sql_import foreignkey-stats --clean-unused`
- **那么** 删除超过 30 天未使用的策略
- **并且** 更新 `metadata.json`

### 需求：外键信息数据结构

系统必须定义标准的外键信息数据结构（Pydantic Schema）。

#### 场景：外键数据模型

- **当** 创建外键信息对象
- **那么** 必须包含以下字段：
  - `constraint_name: str`：约束名称（必填）
  - `source_table: str`：源表名（必填）
  - `source_columns: List[str]`：源字段列表（必填，至少 1 个）
  - `target_table: str`：目标表名（必填）
  - `target_columns: List[str]`：目标字段列表（必填，至少 1 个）
  - `on_delete: Optional[str]`：删除规则（可选，枚举值：`cascade`、`set_null`、`restrict`、`no_action`）

#### 场景：表外键信息模型

- **当** 创建表的外键信息对象（按表存储）
- **那么** 必须包含以下字段：
  - `table_name: str`：表名（必填）
  - `source_file: str`：源文件名（必填）
  - `foreign_keys: List[ForeignKey]`：外键列表（可为空）
  - `extracted_at: datetime`：提取时间（自动生成）

#### 场景：统一外键信息模型

- **当** 创建统一外键信息对象（统一存储）
- **那么** 必须包含以下字段：
  - `metadata: dict`：元数据（提取时间、统计信息）
  - `foreignkeys: List[dict]`：外键列表（包含 `source_file` 字段）

#### 场景：字段验证

- **当** 创建外键对象时 `source_columns` 和 `target_columns` 长度不一致
- **那么** 抛出验证错误
- **当** `on_delete` 值不在枚举范围内
- **那么** 抛出验证错误

### 需求：大文件优化处理

系统必须优化大型 SQL 文件（>1MB）的处理，使用关键字片段提取和流式处理，避免内存溢出。

#### 场景：文件大小检测

- **当** 开始处理 SQL 文件
- **那么** 检测文件大小（字节转换为 MB）
- **并且** 根据大小选择处理策略：
  - ≤1MB：正常读取整个文件
  - >1MB：启用流式处理和片段提取

#### 场景：流式关键字搜索

- **当** 处理大文件
- **那么** 逐行读取文件（不一次性加载到内存）
- **并且** 使用正则表达式搜索外键关键字
- **并且** 关键字包括（不区分大小写）：
  - `foreign\s+key`
  - `references\s+\w+`
  - `add\s+constraint.*foreign`
  - `constraint.*references`

#### 场景：上下文提取

- **当** 找到包含外键关键字的行
- **那么** 提取该行的上下文：
  - 前 5 行
  - 当前行
  - 后 10 行
- **并且** 确保提取到完整的 SQL 语句（查找分号）
- **并且** 如果没有分号，继续向后读取直到找到分号

#### 场景：片段数量限制

- **当** 提取到多个外键片段
- **那么** 去除重复片段
- **并且** 最多保留 5 个示例片段
- **并且** 优先保留格式最清晰、最完整的片段

#### 场景：片段 Token 估算

- **当** 准备发送片段给 LLM
- **那么** 估算片段的 Token 数量（约 1 字符 = 0.4 token）
- **并且** 如果总 Token 数 > 4000
- **那么** 减少片段数量或截断片段
- **并且** 确保每个片段至少包含一个完整的外键定义

#### 场景：流式应用提取脚本

- **当** 对大文件应用提取脚本
- **那么** 使用分块读取（每块 1MB）
- **并且** 对每块应用提取脚本
- **并且** 累积提取结果（而非累积文件内容）
- **并且** 确保内存占用稳定在 100MB 以内

#### 场景：大文件性能监控

- **当** 处理大文件
- **那么** 记录以下性能指标：
  - 文件大小
  - 片段提取耗时
  - 提取脚本应用耗时
  - 内存峰值使用量
- **并且** 在详细日志中输出这些指标

#### 场景：极大文件处理（>10MB）

- **当** 文件大小 > 10MB
- **那么** 输出警告信息（处理时间可能较长）
- **并且** 增加片段提取的跳过步长（减少提取密度）
- **并且** 考虑并行处理（如果支持）
