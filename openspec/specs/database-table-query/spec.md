# 数据库表查询管理

## 目的

数据库表查询管理系统允许用户通过配置化的方式查询和展示导入的医院数据，无需为每个表单独编写代码。系统支持动态表结构检测、字段映射、中文名称配置、数据查询、导出和日志记录等功能，提供完整的表数据查询解决方案。
## 需求
### 需求：表查询配置管理

系统必须提供 JSON 配置方式定义表的查询规则，包括可见字段、可搜索字段、排序字段等。

#### 场景：创建表查询配置

- **当** 管理员创建新的表查询配置
- **那么** 系统保存配置到 `table_query_config` 表
- **并且** 配置包含表名、显示名称、字段定义、分页设置等

#### 场景：批量创建配置

- **当** 使用 `batch_create_table_configs` 命令
- **那么** 系统自动检测表结构并批量生成配置
- **并且** 支持按表名前缀过滤
- **并且** 表的中文显示名称（`display_name`）按以下优先级获取：
  1. 数据库表的 COMMENT（如果存在）
  2. meaning.json 文件中的 `inferred_meaning`（如果指定了 `--meaning-dir` 且文件存在）
  3. JSON 配置文件中 `tables` 部分的映射（如果配置文件存在且包含该表）
  4. 表名本身

#### 场景：从数据库 COMMENT 获取表名

- **当** 执行 `batch_create_table_configs` 命令
- **那么** 系统查询 `INFORMATION_SCHEMA.TABLES` 获取表的 `TABLE_COMMENT`
- **并且** 如果 COMMENT 存在且非空，使用 COMMENT 作为表的 `display_name`

#### 场景：从 meaning.json 获取表名

- **当** 执行 `batch_create_table_configs` 命令并指定 `--meaning-dir` 参数
- **那么** 系统扫描目录下所有 `*_meaning.json` 文件
- **并且** 解析 JSON 文件中的 `table.inferred_meaning` 作为表的中文名称
- **并且** 如果数据库 COMMENT 不存在，使用 meaning.json 中的含义作为 `display_name`

#### 场景：从配置文件获取表名

- **当** 执行 `batch_create_table_configs` 命令并指定 `--config-file` 参数
- **那么** 系统读取 JSON 配置文件
- **并且** 如果配置文件的 `tables` 部分包含该表的映射，使用映射值作为 `display_name`
- **并且** 如果配置文件不存在或格式错误，降级使用默认逻辑（COMMENT 或表名）

#### 场景：字段中文名称配置

- **当** 批量创建表配置时
- **那么** 字段配置中的 `displayName` 按以下优先级获取：
  1. 数据库字段的 `COLUMN_COMMENT`（如果存在）
  2. meaning.json 文件中对应字段的 `inferred_meaning`（如果指定了 `--meaning-dir` 且文件存在）
  3. JSON 配置文件中 `fields[table_name][field_name]` 的映射（如果配置文件存在且包含该映射）
  4. 字段名本身
- **并且** 如果字段 COMMENT 或配置文件中存在中文名称，使用该名称作为 `displayName`

#### 场景：配置文件格式

- **当** 使用 `--config-file` 参数指定配置文件
- **那么** 配置文件必须是有效的 JSON 格式
- **并且** 配置文件结构包含 `tables` 和 `fields` 两个部分：
  - `tables`: 对象，键为表名，值为中文名称
  - `fields`: 对象，键为表名，值为对象，内层对象键为字段名，值为中文名称
- **并且** 如果配置文件格式错误，命令显示警告并继续使用默认逻辑

### 需求：动态查询 API

系统必须提供统一的查询 API，支持根据配置动态查询数据库表。

#### 场景：执行分页查询

- **当** 用户请求 `POST /api/core/table-query/query`
- **那么** 系统验证配置和参数
- **并且** 返回分页数据结果

#### 场景：SQL 注入防护

- **当** 查询参数包含恶意 SQL 代码
- **那么** 系统使用参数化查询和白名单验证
- **并且** 拒绝非法操作符和字段名

#### 场景：MySQL 保留关键字处理

- **当** 表或字段名是 MySQL 保留关键字（如 `partition`、`explain`）
- **那么** 系统自动使用反引号转义标识符
- **并且** SQL 执行正常

#### 场景：过滤字段验证

- **当** 过滤条件中的字段未标记为 `searchable: true`
- **那么** 系统返回 400 错误
- **并且** 错误响应包含可搜索字段列表
- **并且** 调用方可根据返回的字段列表修正请求

### 需求：数据导出

系统必须支持将查询结果导出为 Excel 或 CSV 格式。

#### 场景：导出 Excel

- **当** 用户请求导出为 Excel 格式
- **那么** 系统生成 `.xlsx` 文件
- **并且** 包含表头和数据

#### 场景：导出 CSV

- **当** 用户请求导出为 CSV 格式
- **那么** 系统生成 `.csv` 文件
- **并且** 使用 UTF-8-BOM 编码

### 需求：查询日志

系统必须记录所有查询和导出操作用于安全审计。

#### 场景：记录查询操作

- **当** 用户执行表查询
- **那么** 系统在 `table_query_log` 表记录
- **并且** 包含用户ID、表名、操作类型、过滤条件、记录数、执行时间

### 需求：前端查询页面

系统必须提供前端页面支持表切换和数据展示。

#### 场景：表选择器

- **当** 用户访问表查询页面
- **那么** 左侧显示可查询表的列表
- **并且** 支持按配置中的显示名称展示

#### 场景：动态表格

- **当** 用户选择某个表配置
- **那么** 表格列根据配置动态生成
- **并且** 支持分页、排序功能
- **并且** 表格列标题同时显示字段的中文名称（`displayName`）和原始字段名（`name`）
- **并且** 列标题显示格式为：`中文名称 (字段名)`，如果中文名称与字段名相同或为空，则只显示字段名

#### 场景：动态搜索表单

- **当** 表配置包含可搜索字段
- **那么** 搜索表单动态生成对应的输入控件
- **并且** 根据字段类型选择合适的组件
- **并且** 搜索表单标签显示字段的中文名称（`displayName`）

### 需求：外部配置文件支持

系统必须支持通过外部 JSON 配置文件提供表名和字段名的中文映射。

#### 场景：指定配置文件路径

- **当** 执行 `batch_create_table_configs` 命令时
- **那么** 支持 `--config-file` 参数指定配置文件路径
- **并且** 如果未指定，默认使用 `core/management/commands/table_name_mapping.json`
- **并且** 如果默认文件不存在，忽略配置文件，使用其他优先级逻辑

#### 场景：配置文件读取

- **当** 配置文件存在且格式正确
- **那么** 系统读取配置文件内容
- **并且** 在生成表配置时优先使用配置文件中的映射
- **并且** 配置文件读取失败时不影响命令执行，仅显示警告

### 需求：菜单初始化

系统必须支持通过管理命令初始化菜单。

#### 场景：执行菜单初始化

- **当** 运行 `python manage.py init_table_query_menus`
- **那么** 系统创建"数据查询"父菜单
- **并且** 创建"表数据查询"子菜单

### 需求：从 meaning.json 文件加载语义信息

系统必须支持从 `*_meaning.json` 文件批量加载表和字段的中文含义信息。

#### 场景：指定 meaning.json 目录

- **当** 执行 `batch_create_table_configs` 命令时
- **那么** 支持 `--meaning-dir` 参数指定 meaning.json 文件所在目录
- **并且** 如果未指定，默认查找 `docs/hospital/commentsql` 目录
- **并且** 如果目录不存在，忽略 meaning.json 功能，使用其他优先级逻辑

#### 场景：配置数据库表名前缀

- **当** 执行 `batch_create_table_configs` 命令并指定 `--table-prefix` 参数
- **那么** 系统在匹配 meaning.json 时，会先去掉数据库表名的指定前缀
- **并且** 例如数据库表名为 `dbo_XY_TABLE`，指定 `--table-prefix dbo_` 后，会用 `XY_TABLE` 去匹配 meaning.json
- **并且** 如果未指定前缀，直接使用完整表名进行匹配

#### 场景：解析 meaning.json 文件

- **当** 指定的目录存在且包含 `*_meaning.json` 文件
- **那么** 系统扫描并解析所有匹配的 JSON 文件
- **并且** 忽略 `all_meanings.json` 文件（该文件是合并文件，格式不同）
- **并且** 从 `table.table_name` 获取表名
- **并且** 从 `table.inferred_meaning` 获取表的中文含义
- **并且** 从 `table.fields[].field_name` 和 `table.fields[].inferred_meaning` 获取字段的中文含义
- **并且** 构建内存中的映射结构供后续查询使用

#### 场景：meaning.json 文件格式

- **当** 解析 meaning.json 文件时
- **那么** 文件必须包含以下结构：
  ```json
  {
    "table": {
      "table_name": "表名",
      "inferred_meaning": "表的中文含义",
      "fields": [
        {
          "field_name": "字段名",
          "inferred_meaning": "字段的中文含义"
        }
      ]
    }
  }
  ```
- **并且** 如果文件格式不正确，跳过该文件并输出警告

#### 场景：meaning.json 读取失败处理

- **当** meaning.json 文件读取或解析失败
- **那么** 系统输出警告信息
- **并且** 跳过该文件继续处理其他文件
- **并且** 不影响命令的整体执行

### 需求：可搜索字段查询端点

系统必须提供 API 端点查询指定表配置的可搜索字段列表，供 AI Agent 和前端使用。

#### 场景：查询配置的可搜索字段

- **当** 调用 `GET /api/core/table-query/configs/{config_id}/searchable-fields`
- **那么** 返回该配置中所有标记为 `searchable: true` 的字段
- **并且** 每个字段包含 `name`（字段名）、`display_name`（显示名称）、`type`（字段类型）

#### 场景：按名称查询可搜索字段

- **当** 调用 `GET /api/core/table-query/configs/by-name/{name}/searchable-fields`
- **那么** 系统先按名称匹配配置（支持模糊匹配）
- **并且** 返回匹配配置的可搜索字段列表

### 需求：增强的字段搜索错误提示

当查询请求中的过滤字段不支持搜索时，系统必须返回详细的错误信息，包含可用的搜索字段列表。

#### 场景：字段不支持搜索错误响应

- **当** 查询请求的过滤条件包含不支持搜索的字段
- **那么** API 返回 HTTP 400 错误
- **并且** 响应体包含 `detail` 对象
- **并且** `detail.message` 说明哪个字段不支持搜索
- **并且** `detail.available_fields` 数组列出所有可搜索字段的名称

#### 场景：错误响应格式示例

- **当** 使用不支持搜索的字段 `oldername` 进行过滤
- **那么** 返回如下格式的错误响应：

```json
{
  "detail": {
    "message": "字段 oldername 不支持搜索",
    "available_fields": ["id", "name", "create_time"]
  }
}
```

### 需求：自动创建表查询配置和数据导入

系统必须支持自动创建表查询配置和导入数据，无需手动配置。

#### 场景：自动创建问卷类型表

- **当** 问卷系统同步数据到表查询系统时
- **那么** 系统自动检测表是否存在
- **并且** 如果表不存在，根据问卷 Schema 和展开后的字段创建表
- **并且** 表名格式为 `survey_{survey_type}`（如 `survey_personality`）
- **并且** 表结构包含展开后的字段和原始 JSON 字段
- **并且** 自动创建必要的索引

#### 场景：自动生成表查询配置

- **当** 创建新的问卷类型表时
- **那么** 系统自动创建对应的 `TableQueryConfig` 配置
- **并且** 配置的 `table_name` 为 `survey_{survey_type}`
- **并且** 配置的 `display_name` 为问卷名称
- **并且** 配置的 `fields` 列表包含所有展开后的字段
- **并且** 字段配置包含：
  - `name`：展开后的字段名（如 `survey_data_totalScore`）
  - `display_name`：从 Schema 或字段名推断的中文名称
  - `type`：推断的字段类型（string/integer/decimal/boolean/datetime）
  - `searchable`：从 Schema 中获取，默认为 `true`
  - `sortable`：默认为 `true`
  - `visible`：默认为 `true`

#### 场景：数据导入和更新

- **当** 问卷数据同步到表查询系统时
- **那么** 系统将展开后的数据插入或更新到对应的表
- **并且** 使用 `survey_id` 作为唯一标识（如果已存在则更新，否则插入）
- **并且** 支持批量插入以提高性能
- **并且** 保留原始 JSON 字段用于完整数据查询

#### 场景：表结构更新

- **当** 问卷 Schema 变更导致新增字段时
- **那么** 系统检测到新字段后自动添加列到表
- **并且** 更新表查询配置，添加新字段的配置
- **并且** 保留旧字段，标记为已废弃（可选）

#### 场景：字段类型推断

- **当** 从 JSON 数据推断字段类型时
- **那么** 系统根据 JSON 值的类型推断：
  - 字符串：检查是否为日期时间格式，如果是则为 `datetime`，否则为 `string`
  - 数字：整数为 `integer`，小数为 `decimal`
  - 布尔值：`boolean`
  - 对象/数组：保持为 JSON 类型，但展开的字段根据实际值推断
- **并且** 优先使用 Schema 配置中的字段类型
- **并且** 如果 Schema 中未定义，使用推断的类型

#### 场景：字段显示名称映射

- **当** 生成字段配置时
- **那么** 系统按以下优先级获取字段显示名称：
  1. Schema 配置中的字段中文名称
  2. 字段名到中文名称的映射（参考前端 `formatFieldName` 函数）
  3. 字段名本身（驼峰转空格格式）
- **并且** 支持自定义映射规则

#### 场景：支持手动触发同步

- **当** 调用 `POST /api/core/table-query/sync-survey-data` API 时
- **那么** 系统手动触发问卷数据同步到表查询系统
- **并且** 支持指定问卷类型（`survey_type` 参数）
- **并且** 支持全量同步（`full_sync=true`）或增量同步（`full_sync=false`）
- **并且** 返回同步结果（成功数、失败数、错误详情）
