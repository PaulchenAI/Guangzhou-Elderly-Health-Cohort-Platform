## 需求
### 需求：Claude Code CLI核心引擎

系统必须以Claude Code CLI作为核心引擎，提供本地文件操作和coding能力。

#### 场景：文件读取
- **当** 智能体需要读取本地文件
- **那么** 系统必须通过Claude Code CLI读取文件内容
- **并且** 返回文件内容或错误信息

#### 场景：文件写入
- **当** 智能体需要创建或覆盖文件
- **那么** 系统必须通过Claude Code CLI写入文件
- **并且** 返回操作结果

#### 场景：文件编辑
- **当** 智能体需要修改文件部分内容
- **那么** 系统必须通过Claude Code CLI进行精确编辑（字符串替换）
- **并且** 保持文件其他部分不变

#### 场景：文件搜索
- **当** 智能体需要查找文件
- **那么** 系统必须通过Claude Code CLI支持glob模式搜索
- **并且** 返回匹配的文件列表

#### 场景：内容搜索
- **当** 智能体需要在代码库中搜索内容
- **那么** 系统必须通过Claude Code CLI支持正则表达式搜索
- **并且** 返回匹配的文件和行号

#### 场景：代码分析
- **当** 智能体需要理解代码
- **那么** 系统必须通过Claude Code CLI分析代码结构和语义
- **并且** 返回分析结果

#### 场景：代码生成
- **当** 智能体需要生成新代码
- **那么** 系统必须通过Claude Code CLI根据需求和上下文生成代码
- **并且** 代码符合项目规范

#### 场景：代码重构
- **当** 智能体需要重构现有代码
- **那么** 系统必须通过Claude Code CLI分析并重构代码
- **并且** 保持功能不变

#### 场景：并发控制
- **当** 多个请求同时需要调用Claude Code CLI
- **那么** 系统必须控制并发数量
- **并且** 防止资源耗尽

#### 场景：超时处理
- **当** Claude Code CLI执行超时
- **那么** 系统必须终止进程
- **并且** 返回超时错误信息

---

### 需求：多智能体编排框架

系统必须提供基于LangChain + LangGraph的多智能体编排框架，协调各智能体完成复杂任务。

#### 场景：任务编排执行
- **当** 用户提交一个复杂任务
- **那么** 编排智能体必须分析任务并决定执行路径
- **并且** 协调RAG、Memory等智能体提供上下文
- **并且** 最终通过Claude Code CLI执行操作

#### 场景：上下文增强
- **当** 任务需要额外上下文
- **那么** 编排智能体必须先调用RAG或Memory智能体
- **并且** 将检索结果作为Claude Code CLI的输入上下文

#### 场景：智能体通信
- **当** 智能体之间需要传递数据
- **那么** 系统必须通过LangGraph状态传递数据
- **并且** 保证数据一致性

---

### 需求：RAG检索增强

系统必须提供RAG（检索增强生成）能力，从多种知识源检索相关信息增强Claude Code CLI的上下文。

#### 场景：代码库检索
- **当** 需要了解项目代码
- **那么** RAG系统必须从代码库向量索引中检索相关代码片段
- **并且** 返回语义相关的代码和注释

#### 场景：文档检索
- **当** 需要参考文档
- **那么** RAG系统必须从文档知识库检索相关内容
- **并且** 支持Markdown、TXT等格式

#### 场景：数据库元数据检索
- **当** 需要了解数据库结构
- **那么** RAG系统必须检索数据库Schema信息
- **并且** 包括表结构、字段说明、关系等

#### 场景：增量索引更新
- **当** 知识源文件发生变化
- **那么** 系统必须支持增量更新向量索引
- **并且** 无需全量重建

---

### 需求：上下文记忆系统

系统必须提供分层记忆系统，支持短期对话记忆和长期知识记忆。

#### 场景：对话历史保持
- **当** 用户在同一会话中多次交互
- **那么** 系统必须保持对话上下文
- **并且** 后续回复考虑之前的对话内容

#### 场景：长期记忆存储
- **当** 系统学习到重要信息
- **那么** 系统必须将信息存储到长期记忆
- **并且** 在后续会话中可以检索使用

#### 场景：记忆检索
- **当** 智能体需要历史上下文
- **那么** 系统必须从记忆中检索相关信息
- **并且** 按相关性排序返回

#### 场景：记忆容量管理
- **当** 记忆存储接近容量限制
- **那么** 系统必须按策略淘汰旧记忆
- **并且** 优先保留重要信息

---

### 需求：日志记录系统

系统必须提供完善的日志记录能力，支持Claude Code CLI调用追踪和性能监控。

#### 场景：Claude Code CLI调用日志
- **当** 系统调用Claude Code CLI
- **那么** 系统必须记录调用命令、输入、输出、耗时
- **并且** 日志可用于调试和审计

#### 场景：智能体交互日志
- **当** 智能体执行任务
- **那么** 系统必须记录智能体名称、输入、输出、耗时
- **并且** 记录智能体间的调用链

#### 场景：错误日志
- **当** 系统发生错误或异常
- **那么** 系统必须记录完整错误信息和堆栈
- **并且** 支持错误告警

#### 场景：日志查询
- **当** 用户需要查看日志
- **那么** 系统必须支持按时间、智能体、级别等过滤
- **并且** 支持日志导出

---

### 需求：环境变量配置系统

系统必须支持通过.env文件配置Claude Code CLI路径、LLM提供商、数据库连接等信息。

#### 场景：.env文件加载
- **当** 系统启动时
- **那么** 系统必须自动加载.env文件中的环境变量
- **并且** 支持.env.example作为配置模板

#### 场景：Claude Code CLI配置
- **当** 需要配置Claude Code CLI
- **那么** 用户可以通过.env设置CLI路径、超时时间、并发数等
- **并且** 系统启动时验证CLI可用性

#### 场景：通用LLM配置
- **当** 需要配置LLM提供商
- **那么** 用户可以通过.env设置LLM_PROVIDER（anthropic/openai/local等）
- **并且** 通过LLM_API_KEY、LLM_MODEL等通用参数配置
- **并且** 系统根据LLM_PROVIDER自动选择对应的LLM客户端实现
- **并且** 支持本地模型（通过LLM_BASE_URL配置）

#### 场景：多LLM提供商支持
- **当** 用户切换LLM提供商
- **那么** 系统必须支持anthropic、openai、local、azure_openai等多种提供商
- **并且** 无需修改代码，仅需更改.env配置
- **并且** 所有智能体自动使用新的LLM提供商

#### 场景：配置优先级
- **当** 同一配置项在多处定义
- **那么** 系统必须按优先级加载：系统环境变量 > .env文件 > YAML默认值
- **并且** 高优先级配置覆盖低优先级

#### 场景：配置缺失处理
- **当** 必需的环境变量未配置
- **那么** 系统必须在启动时给出明确错误提示
- **并且** 指明缺失的配置项名称

### 需求：OpenSpec集成

系统必须集成OpenSpec，支持将复杂任务拆解为多个变更提案并进行管理。

#### 场景：任务拆解为提案
- **当** Planning Agent识别到复杂任务
- **那么** 系统必须将任务拆解为多个独立的OpenSpec变更提案
- **并且** 每个提案符合OpenSpec规范格式
- **并且** 识别提案间的依赖关系

#### 场景：创建OpenSpec提案
- **当** 需要创建新的变更提案
- **那么** 系统必须生成完整的提案结构（proposal.md, tasks.md, specs/）
- **并且** 提案内容符合OpenSpec规范
- **并且** 自动验证提案格式

#### 场景：验证OpenSpec提案
- **当** 创建或修改OpenSpec提案后
- **那么** 系统必须调用openspec-cn validate验证提案
- **并且** 返回验证结果和错误信息（如有）

#### 场景：检查提案冲突
- **当** 创建新提案前
- **那么** 系统必须检查与现有活动提案的冲突
- **并且** 识别重叠的规范变更
- **并且** 提供冲突解决建议

#### 场景：提案执行计划
- **当** 有多个提案需要执行
- **那么** 系统必须分析提案依赖关系
- **并且** 生成按依赖排序的执行计划
- **并且** 识别可并行执行的提案

#### 场景：提案进度跟踪
- **当** 提案执行过程中
- **那么** 系统必须跟踪tasks.md中的任务完成情况
- **并且** 生成进度报告
- **并且** 识别阻塞任务

#### 场景：提案归档
- **当** 提案执行完成
- **那么** 系统必须支持归档提案
- **并且** 调用openspec-cn archive命令
- **并且** 更新规范到specs/目录

### 需求：YAML配置系统

系统必须支持通过YAML文件配置Prompts模板、智能体行为和工作流定义。

#### 场景：Prompts配置
- **当** 需要修改智能体Prompts
- **那么** 用户可以编辑YAML配置文件
- **并且** 系统自动加载新配置无需重启

#### 场景：智能体配置
- **当** 需要调整智能体参数
- **那么** 用户可以通过YAML配置温度、最大Token等
- **并且** 配置支持环境变量覆盖

#### 场景：工作流配置
- **当** 需要定义新的智能体协作流程
- **那么** 用户可以通过YAML定义工作流步骤和条件
- **并且** 系统按配置执行

#### 场景：配置验证
- **当** 加载配置文件
- **那么** 系统必须验证配置格式和必填字段
- **并且** 对无效配置给出明确错误信息

### 需求：Django API 集成

系统必须提供 OpenAPI-Aware 的 Django API 客户端，使智能体能够自动理解并调用 backend-django 后台 API。

#### 场景：加载 OpenAPI Schema
- **当** 客户端初始化时
- **那么** 系统必须从 Django API 的 `/api/openapi.json` 端点获取 OpenAPI Schema
- **并且** 解析 Schema 构建 API 端点索引
- **并且** 支持按 operation_id 和 tag 检索端点

#### 场景：生成 AI 可理解的 API 摘要
- **当** 智能体需要了解可用 API
- **那么** 系统必须将 OpenAPI Schema 转换为 AI 可理解的文本描述
- **并且** 包含 API 分类、端点列表、功能说明
- **并且** 描述格式适合作为 LLM 的系统提示词

#### 场景：API 端点搜索
- **当** 需要查找特定功能的 API
- **那么** 系统必须支持按关键词搜索 API 端点
- **并且** 搜索范围包括 operation_id、summary、description、path、tags
- **并且** 返回匹配的端点列表

#### 场景：意图到 API 匹配
- **当** 用户表达操作意图（如"查询用户列表"）
- **那么** 系统必须将意图匹配到对应的 API 端点
- **并且** 支持关键词匹配（快速）
- **并且** 支持 LLM 辅助匹配（智能）

#### 场景：大规模 API 的 RAG 检索
- **当** OpenAPI Schema 包含大量端点（超过 50 个）
- **那么** 系统必须使用分层检索策略
- **并且** 第一层通过关键词/tag 快速过滤候选集
- **并且** 第二层通过向量相似度检索最相关的端点
- **并且** 最终返回 Top-K 个最匹配的 API 端点供 LLM 选择

#### 场景：API 端点向量索引
- **当** 加载 OpenAPI Schema 后
- **那么** 系统必须为每个 API 端点生成向量表示
- **并且** 向量内容包括 operation_id、summary、description、path、tags
- **并且** 支持增量更新索引（Schema 变化时）

#### 场景：语义检索 API
- **当** 用户查询与 API 描述语义相关但关键词不匹配
- **那么** 系统必须通过向量相似度找到语义相关的 API
- **并且** 返回相似度分数用于排序

#### 场景：Bearer Token 认证
- **当** 需要调用受保护的 API
- **那么** 系统必须先通过登录 API 获取 access_token
- **并且** 在后续请求中自动附加 Authorization 头
- **并且** 支持 Token 刷新（当 Token 过期时）

#### 场景：通用 API 调用
- **当** 确定要调用的 API 端点
- **那么** 系统必须根据 OpenAPI Schema 自动处理参数
- **并且** 正确区分路径参数、查询参数、请求体
- **并且** 使用正确的 HTTP 方法发送请求
- **并且** 返回 API 响应数据

#### 场景：根据意图调用 API
- **当** 用户提供操作意图和参数
- **那么** 系统必须自动匹配 API 端点
- **并且** 自动分配参数到正确位置
- **并且** 执行 API 调用并返回结果

### 需求：Django API 智能体

系统必须提供 Django API 智能体，集成 LLM 进行意图理解和 API 调用决策。

#### 场景：智能体初始化
- **当** 创建 Django API 智能体
- **那么** 系统必须自动加载 OpenAPI Schema
- **并且** 自动完成登录认证
- **并且** 准备好接收用户查询

#### 场景：生成系统提示词
- **当** 需要与 LLM 交互
- **那么** 系统必须生成包含 API 能力描述的系统提示词
- **并且** 提示词包含可用 API 列表和调用格式
- **并且** 指导 LLM 返回结构化的调用决策

#### 场景：处理用户查询
- **当** 用户提交自然语言查询
- **那么** 智能体必须理解用户意图
- **并且** 选择合适的 API 端点
- **并且** 构造正确的参数
- **并且** 执行 API 调用并返回结果

---

### 需求：Django API 配置

系统必须支持通过配置文件和环境变量配置 Django API 连接信息。

#### 场景：YAML 配置
- **当** 需要配置 Django API 连接
- **那么** 用户可以在 `config/settings.yaml` 中配置
- **并且** 支持 base_url、username、password、timeout 等参数

#### 场景：环境变量配置
- **当** 需要覆盖默认配置
- **那么** 用户可以通过环境变量配置
- **并且** 环境变量优先级高于 YAML 配置
- **并且** 支持 DJANGO_API_BASE_URL、DJANGO_API_USERNAME、DJANGO_API_PASSWORD 等变量

#### 场景：配置验证
- **当** 加载 Django API 配置
- **那么** 系统必须验证必填配置项
- **并且** 对缺失的必填项给出明确错误提示
